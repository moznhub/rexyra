# Compatibility with Redis

Rexyra aims to behave like Redis 7.x for the commands it implements: replies and error messages are compared with Redis 7.4 byte for byte. This page lists everything known to differ, and how persistence, the memory limit and access control behave.

If you find a difference that is not listed here, please [report it](../CONTRIBUTING.md#ways-to-help).

## Not implemented

Rexyra is a single-instance server. Replication, Sentinel, cluster mode, streams, HyperLogLog, geospatial commands, modules and TLS are not implemented. See the [roadmap](ROADMAP.md).

Also not implemented yet, found by the [client library tests](../clients/README.md):

- `WAIT`, `LATENCY`, `CLIENT PAUSE` / `UNPAUSE`, `MONITOR`.

## Known differences

- `INCRBYFLOAT` formats results with the shortest text that round-trips as a 64-bit float. Redis uses 80-bit `long double`, so a few results differ in the last digits (for example `0.1 + 0.2`).
- Active expiry is exact (keys are removed in expiry order within about 100 ms) rather than sampled.
- `FLUSHDB ASYNC` and `FLUSHALL ASYNC` hand the data to a background thread to free; `UNLINK` does the same for collections of more than 64 elements and frees smaller values on the spot.
- `OBJECT ENCODING` reports the name Redis would use (`int`, `embstr`, `raw`), not the internal representation. `OBJECT IDLETIME` and `OBJECT FREQ` each answer only under the kind of eviction policy Redis answers them under (LRU-style and LFU respectively), with the same errors otherwise.
- `OBJECT ENCODING` for a list reports `listpack` or `quicklist` from an estimate of its size; internally every list is a double-ended queue.
- `SCAN` cursors are valid but not numerically equal to Redis's, and `SCAN ... TYPE` keeps scanning until it has `COUNT` matches (within a work budget) instead of stopping after `COUNT` keys.
- `HRANDFIELD`, `SRANDMEMBER` and `ZRANDMEMBER` with a positive count on a large collection take time proportional to its size.
- Blocking commands do not accept a hexadecimal timeout (`0x10`), which Redis does.
- `WATCH` treats a write command that turned out to change nothing as no change, as Redis does, for the commands compared against Redis so far; a command not yet covered errs on the side of aborting the transaction.
- `SORT` weights do not accept hexadecimal numbers. With `BY ... ALPHA`, elements whose `BY` values are equal keep their original relative order; Redis leaves that order unspecified.
- `INFO` reports the sections and fields this server has real figures for. `used_memory` is what the process has allocated, counted by the allocator (the Lua interpreter's own memory is not included); `used_memory_rss` is what the operating system reports. `avg_ttl` is always 0; there are no CPU or hit/miss figures yet.
- `CONFIG SET` changes `maxclients`, `slowlog-log-slower-than`, `slowlog-max-len`, `save`, `appendonly`, `appendfsync`, `auto-aof-rewrite-percentage`, `auto-aof-rewrite-min-size`, `maxmemory`, `maxmemory-policy`, `maxmemory-samples`, `lfu-log-factor`, `lfu-decay-time`, `requirepass`, `protected-mode`, `notify-keyspace-events`, `tracking-table-max-keys`, `rdb-key-save-delay` (a test aid: microseconds the background save's writer pauses per key, to stand in for a slow disk) and `busy-reply-threshold` (also as `lua-time-limit`). Other parameters `CONFIG GET` lists describe fixed behaviour and cannot be set; parameters it does not list are not implemented.
- `CONFIG REWRITE` rewrites the configuration file as Redis does: lines already there are updated where they are, comments and unknown directives are kept, extra lines are blanked, and settings that differ from their default are added after `# Generated by CONFIG REWRITE`, followed by every user. The file is replaced in one step, through a temporary file beside it. Text values are written bare or in single quotes where that is safe (`dir C:\ProgramData\Rexyra\data`) rather than always in double quotes, which would double every backslash of a Windows path; Redis reads both. Rexyra's own settings (`logfile-max-size`, ...), `logfile`, the fixed parameters such as `hz`, and `rdb-key-save-delay` are left as they are in the file.
- `SWAPDB` waits while a background save or rewrite is reading the data, as a write to a large collection does (below). Inside `MULTI`/`EXEC` or a script it cannot wait, and is refused with an error until that part of the save is over.
- `CLIENT LIST` and `CLIENT INFO` report socket and input buffer sizes (`fd`, `qbuf`, `argv-mem`, ...) as 0. `omem` (and `tot-mem`) is the output handed to the connection and not yet written to its socket.
- `MEMORY USAGE` is an estimate from the lengths of keys and values, not an allocator measurement.
- A configuration file may contain directives this server does not support; they are skipped with a warning at start-up instead of stopping the server.
- The log file is rolled by size by the server itself (`logfile-max-size`, `logfile-max-files`; Rexyra's own settings), as Windows has no `logrotate`. Redis leaves that to an outside tool and has no such settings. `syslog-*` directives are skipped like other unsupported ones.
- Scripts run on real Lua 5.1. The `cjson`, `cmsgpack`, `struct` and `bit` libraries are reimplemented in Rust to behave like the originals; `cjson.encode` of a decoded `-0` gives `0` where Redis gives `-0`, and `cjson`'s tuning functions (`encode_sparse_array` and the like) are not provided.
- While a script runs past `busy-reply-threshold` (5 seconds by default), other clients get a `BUSY` error and `SCRIPT KILL` can stop it, as in Redis. `SHUTDOWN NOSAVE`, Redis's way out of a script that has already written, is not implemented, so such a script has to finish or the server process has to be stopped.
- Snapshots are saved in the background automatically, by default after 3600 seconds if 1 key changed, 300 seconds if 100 did, or 60 seconds if 10000 did (`save`, as in Redis), and on `BGSAVE`, `SAVE`, `SHUTDOWN` and Ctrl+C. With only snapshots, a crash or a killed process loses what changed since the last one.
- The append-only file (`--appendonly yes`, off by default as in Redis) logs every change and is replayed at start-up. With `appendfsync always` a write is on disk before its reply is sent; with `everysec`, the default, a crash can lose about the last second; with `no`, whatever the operating system had not written.
- The log uses Redis 7's layout (`appendonlydir` with a manifest, a base snapshot and incremental files), and each server loads the other's. Commands are logged in a replay-safe form, as Redis does: relative expiries as absolute times, `SPOP` as `SREM`, float increments as their result, scripts as the commands they ran inside `MULTI`/`EXEC`, and expired keys as `DEL`. The exact text can differ from what Redis would log for the same commands.
- A log that ends in the middle of a command (the usual result of a crash) is cut back to the last complete command at start-up, with a warning; `aof-load-truncated no` refuses to start instead. A log damaged anywhere else, or containing a command this server does not have, stops the server from starting. There is no repair tool yet.
- `BGREWRITEAOF` when the append-only file is off replies with an error; Redis rewrites anyway. Only one background job (save or rewrite) runs at a time.
- `BGSAVE` does not use `fork`, which Windows lacks. The command thread walks the keyspace a little at a time between commands and captures any key first if a command is about to change it, so the file is the data exactly as it was when the save began; a writer thread does the disk work, and commands never wait for the disk. Measured under load, throughput during a save is 2–7 % below normal and the 99th-percentile latency is unchanged, including with 100 MB strings in the keyspace and with a slowed disk ([benchmarks](benchmarks/bgsave)).
- A list, hash, set or sorted set with thousands of elements (4,096 or more, or about 256 KB) is captured a piece at a time during a save, so it does not hold other clients up. A client that writes to one before the save has captured it waits until it has been, about a tenth of a second for a hash of a million fields, while the other clients see pauses of a few milliseconds. A write from inside `MULTI`/`EXEC` or a script cannot wait, nor can expiry or eviction: there the collection is captured in one go and every client waits (about 85 ms for a hash of a million fields). Strings have no such cost at any size.
- A save in progress uses up to 16 MB for what it has read ahead of the disk, plus the old versions of whatever commands change while it runs, until they are written: a save during heavy overwriting, or onto a slow disk, can hold a copy of everything that was overwritten. Nothing stays allocated after a save. `FLUSHALL` or `FLUSHDB` during a save abandons it and starts a new one right after.
- A crash or kill during a save leaves the previous snapshot in place. The unfinished `temp-*.rdb*` file it leaves behind is removed, with a warning, the next time the server starts on that directory. A new snapshot replaces the old one in a single rename, after its contents are on disk, and the directory is flushed afterwards. A data directory is for one server at a time.
- In a background-saved file the keys of different databases can be interleaved, with a database-selection marker wherever they switch. Redis loads this; it is only unusual to look at.
- Snapshot files use the RDB format and load in Redis 7, and snapshots written by Redis 7 load here. Files from Redis older than 7.0 that use its retired compact encodings, and files containing streams or module data, are refused with a message saying why.
- A snapshot that holds hash fields with a TTL of their own is written in RDB format 12, which Redis 7.4 introduced for them, and loads in Redis 7.4 and later only; one without is written in format 11, as before, and loads in Redis 7.0 and later. Fields whose TTL has passed are left out when a snapshot is loaded or a value restored, as in Redis. A small hash whose field TTLs have all been removed with `HPERSIST` is saved as a plain hash, so after a restart `OBJECT ENCODING` says `listpack` where Redis keeps saying `listpackex`.
- `DUMP` payloads restore on Redis and the other way round, but are not byte-identical to Redis's for the same value, because this server writes the plain encodings. A small hash with field TTLs is the exception: it is written in Redis 7.4's own listpack form.
- A snapshot that cannot be read stops the server at start-up instead of starting empty.
- `SHUTDOWN` replies `OK` before the connection closes; Redis closes it without a reply. It saves only if something changed since the last save, unless `SAVE` or `NOSAVE` is given.
- `FUNCTION LIST` shows a library's functions in the order they were registered, and libraries by name; Redis's order is unspecified.
- Either `SCRIPT KILL` or `FUNCTION KILL` stops whatever is running, script or function; Redis requires the matching one.
- A script cannot create globals by assignment or with `rawset`, as in Redis, but could still replace the globals' metatable with `setmetatable(_G, ...)`, which Redis forbids.
- Sorted sets always use a skip list internally; `OBJECT ENCODING` reports `listpack` while the set is within Redis's compact-encoding thresholds.

## Hash field expiry

`HEXPIRE`, `HPEXPIRE`, `HEXPIREAT`, `HPEXPIREAT`, `HTTL`, `HPTTL`, `HEXPIRETIME`, `HPEXPIRETIME` and `HPERSIST` reply as in Redis 7.4, errors and their order included, in RESP2 and RESP3. A field past its TTL is treated as Redis 7.4 treats it until it is reclaimed: `HGETALL`, `HKEYS`, `HVALS`, `HSCAN`, `SORT ... BY/GET` and `HTTL` leave it out; `HGET`, `HMGET`, `HEXISTS`, `HSTRLEN`, `HSETNX`, `HINCRBY` and `HINCRBYFLOAT` delete it when they look it up; `HRANDFIELD` deletes every such field of the hash first; `HLEN` still counts it, `HSET` and `HDEL` count it as there, and `HEXPIRE` can give it a new TTL. `HSET` removes a field's TTL, `HINCRBY` and `HINCRBYFLOAT` keep it. In a small hash, fields with a TTL come first in `HGETALL`, by time, as in Redis's `listpackex` encoding. `INFO` reports `subexpiry` per database and `expired_subkeys`, and a field reclaimed counts as a change of its key for `WATCH`.

- Fields are reclaimed like keys: exactly, the hash whose earliest field is due first, within about 100 ms, by the same background cycle, which takes at most 2,000 fields per database per tick (20,000 a second), so a hash with a million fields due never holds commands up; until then they stay counted by `HLEN`. Redis's cycle adapts its effort instead.
- Field TTLs take more memory than in Redis. Measured with `used_memory`: a small hash's first field TTL about 130 bytes and each further one 8, and in a hash of more than 512 fields about 160 bytes per field with a TTL; Redis 7.4 takes about 45 and 13. A hash with no field TTLs costs nothing extra.
- The append-only file logs field TTLs as absolute `HPEXPIREAT`, deleted and reclaimed fields as `HDEL`, `HPERSIST` only for the fields it changed, and `HINCRBYFLOAT` on a field with a TTL as `HSET` and `HPEXPIREAT` in `MULTI`/`EXEC`, as Redis does. `SORT ... STORE` with `BY` or `GET` is logged as its result, since it may have read fields or keys past their TTL that replay would find still there.

## Pub/Sub

`SUBSCRIBE`, `PSUBSCRIBE`, `SSUBSCRIBE`, their `UNSUBSCRIBE` counterparts, `PUBLISH`, `SPUBLISH` and `PUBSUB` behave as in Redis: messages are arrays in RESP2 and push frames in RESP3; a RESP2 connection that has subscribed may only manage its subscriptions, `PING`, `QUIT` and `RESET`; in RESP3 every command stays available. Sharded channels, which exist for cluster mode, are a separate set of channels on a single server. Messages are not stored: one published while nobody listens is lost.

- A subscriber whose unread output passes 32 MB, or stays over 8 MB for 60 seconds, is disconnected: Redis's default `client-output-buffer-limit` for the `pubsub` class. The limit cannot be changed yet, and ordinary clients have none, as in Redis by default.
- `COMMAND INFO` reports the key specifications, legacy key positions, ACL categories and flags (`movablekeys` included) of every command as Redis 7.4 does, in RESP2 and RESP3, and `COMMAND GETKEYS` and `GETKEYSANDFLAGS` find the same keys with the same flags and errors, also where Redis reads the keys with a procedure of the command's own (`SORT ... STORE`, `SET ... GET`, `BITFIELD`, a `numkeys` that is not a plain number); `tools/compare-command-info.py` compares them all with a Redis server. The differences: the command tips and the subcommands of containers (`CONFIG GET`, `OBJECT ENCODING`, ...) are not listed, and `GETKEYS` of a subcommand Rexyra does not have (`MEMORY STATS`) says `Invalid command specified`.
- `DEBUG` has two subcommands: `PANIC`, for testing what happens after an internal error, and `SET-ACTIVE-EXPIRE 0|1`, which stops and restarts the periodic deletion of expired keys so that a test can see keys expire when they are looked up. As in Redis it is refused unless `enable-debug-command` is `yes`, or `local` for connections from the same machine, which can only be set in the configuration file or on the command line.
- After an internal error (a panic), on any thread, the server logs it and the process exits with code 70, so that a service set to restart on failure is started again from the data on disk. Redis likewise stops on an internal error.
- The order of the channels in `PUBSUB CHANNELS` and of the replies to `UNSUBSCRIBE` without arguments is by name, and `ACL CAT pubsub` lists the commands in table order; in Redis these orders are unspecified.

### Keyspace notifications

`notify-keyspace-events` (in the configuration file, on the command line, or with `CONFIG SET`; empty, so off, by default) takes Redis's class letters: `K` and `E` for the `__keyspace@<db>__:<key>` and `__keyevent@<db>__:<event>` channels, `g $ l s h z` for the commands of each type, `x` expired, `e` evicted, `m` key miss, `n` new key, `t` and `d` (accepted, though there are no streams or module types to report), and `A` for `g$lshzxetd`. It is parsed, normalised (`CONFIG GET` shows `KEA` as `AKE`) and refused (`Invalid event class character`) exactly as in Redis, and `CONFIG REWRITE` writes it back.

Every command Rexyra has raises the events Redis 7.4 raises, with the same names, classes and order, including those of a list, set, sorted set or hash emptied by a command (`del`), of `*STORE` commands with an empty result (`del`), of blocking commands when they are served, and of commands run by `MULTI`/`EXEC`, scripts and functions. `FLUSHDB`, `FLUSHALL` and `SWAPDB` raise none, as in Redis. Hash fields raise Redis 7.4's events: `hexpire` when TTLs are set, `hpersist` when one is removed, `hdel` for fields a time already past deletes, and `hexpired` when fields are deleted because their TTL passed (once per hash per lookup or cycle), each followed by `del` if the hash is left empty. `expired` is raised when a key whose TTL has passed is deleted, whether a lookup found it or the periodic cycle did; `evicted` when `maxmemory` removes a key. The messages go through Pub/Sub like any other, so patterns, RESP2 and RESP3, channel permissions and the output limit apply; a client subscribed to its own events gets them after the reply of the command that caused them (after the whole of `EXEC`'s), as in Redis 7.2 and later.

This was checked with [rexyra-keyevents](../tools/rexyra-keyevents/src/main.rs), which runs [a script covering every command](../tools/rexyra-keyevents/scripts/all.txt) against Rexyra and against Redis 7.4 and records the exact stream of notifications, with `KEA`, `KEAmn` and each class on its own. The streams are identical. Differences that remain:

- Keys removed by the periodic expiry cycle are announced in the order they expire, as that cycle is exact here (see above); Redis samples keys at random.
- No notification is ever published while data is being loaded at start-up: Rexyra accepts connections only once loading is over. (Redis lets a client subscribe during loading, and it may see events from the append-only file being replayed.)
- The events of commands Rexyra does not have (streams, geospatial, HyperLogLog, modules) are not raised.

## Client-side caching

`CLIENT TRACKING` with all its options (`REDIRECT`, `BCAST`, `PREFIX`, `OPTIN`, `OPTOUT`, `NOLOOP`), `CLIENT CACHING`, `CLIENT GETREDIR` and `CLIENT TRACKINGINFO` behave as in Redis 7.4: the same errors in the same order of checks, the same invalidation messages (RESP3 pushes, or `__redis__:invalidate` Pub/Sub messages to a RESP2 redirect target, `tracking-redir-broken` when the target has gone, a null invalidation for `FLUSHDB` and `FLUSHALL`), sent to the same connections in the same order relative to replies and keyspace notifications, broadcast once per pass of the execution loop with the keys of each prefix sorted. `CLIENT LIST` shows the `t`, `B` and `R` flags and `redir`; `INFO` has `tracking_clients`, `tracking_total_keys`, `tracking_total_items` and `tracking_total_prefixes`; `tracking-table-max-keys` limits the table as in Redis. go-redis's and redis-py's client-side caches work.

This was checked with [rexyra-tracking](../tools/rexyra-tracking/src/main.rs), which runs [scripts](../tools/rexyra-tracking/scripts) on several connections against Rexyra and Redis 7.4 and records everything each connection receives. The transcripts are identical except for:

- the keys `tracking-table-max-keys` drops, which both servers pick at random;
- when several clients that broadcast with `NOLOOP` change the same key between two broadcasts, Rexyra sends it to each of them, where Redis leaves it out for the client that changed it last;
- the order in which different connections receive their messages, which no client can observe.

## Memory limit

- `maxmemory` (off by default) is compared with what the process has allocated. Before each command, keys are evicted according to `maxmemory-policy` until use is back under the limit; if nothing can be evicted, commands that may add data are refused with `OOM command not allowed when used memory > 'maxmemory'.` while reads and deletes still work. The same applies inside `MULTI` (the transaction is discarded) and to the first write of a script.
- The policies are Redis's: `noeviction` (the default), `allkeys-lru`, `allkeys-lfu`, `allkeys-random`, `volatile-lru`, `volatile-lfu`, `volatile-random` and `volatile-ttl`. LRU and LFU are approximate, as in Redis: `maxmemory-samples` keys (5 by default) are sampled from each database and the best candidate among them goes. Unlike Redis there is no pool of candidates carried over between evictions, so with few samples the choice is a little less precise; `volatile-ttl` on the other hand is exact here.
- Every key carries both its last access time and an access-frequency counter (Redis's logarithmic counter, tuned by `lfu-log-factor` and `lfu-decay-time`), so switching between LRU and LFU policies takes effect at once.
- Evicted keys are written to the append-only file as `DEL` and counted in `evicted_keys`. At most 1000 keys are evicted on behalf of one command; a larger overshoot (after lowering `maxmemory`, say) is worked off over the next commands.
- The limit covers everything the process allocates: data, but also connection buffers and bookkeeping. A string value of 1000 bytes takes about 1330 bytes in all. There are no per-client buffer limits yet, so a client that sends a very large pipeline can still push the process past `maxmemory` for a moment.

## Security

- The server listens on `127.0.0.1` unless `--bind` says otherwise. With protected mode on (the default) and no password set, connections from other machines are answered with a `-DENIED` error explaining what to do, and closed. Setting a password or `protected-mode no` lifts that.
- `requirepass` sets the password of the `default` user; `AUTH password`, `AUTH user password` and `HELLO ... AUTH user password` log in. Until then every command except `AUTH`, `HELLO`, `QUIT` and `RESET` is answered with `NOAUTH Authentication required.`. Connections made while no password was needed stay logged in when one is set, as in Redis.
- ACL users are created with `ACL SETUSER` or `user` lines in the configuration file, using Redis's rule syntax: `on`/`off`, `>password`, `<password`, `#hash`, `!hash`, `nopass`, `resetpass`, `~pattern`, `%R~pattern`, `%W~pattern`, `allkeys`, `resetkeys`, `+command`, `-command`, `+command|subcommand`, `+@category`, `-@category`, `allcommands`, `nocommands`, `reset`. Passwords are kept only as SHA-256 hashes and compared in constant time. `ACL LIST`, `ACL GETUSER` and the error messages match Redis 7.4.
- Permissions are checked for every command, again when a queued transaction runs, and for each command a script calls (scripts run with the caller's permissions). `ACL DELUSER` closes the user's connections.
- Differences from Redis: a command is checked as a whole for key access, so a command that writes needs write permission on every key it names, including those it only reads (`COPY` or `LMOVE` sources, for example). The category lists (`ACL CAT`) follow Redis for the commands this server has but are derived from this server's command table, so a few commands may sit in slightly different categories. Channel rules (`&pattern`, `allchannels`, `resetchannels`) apply to `PUBLISH`, `SPUBLISH`, `SUBSCRIBE`, `SSUBSCRIBE` and `PSUBSCRIBE` (a pattern must be allowed exactly as written), and a subscriber whose user loses access to one of its channels is disconnected, as in Redis. Selectors (rules in parentheses) are rejected.
- Users created with `ACL SETUSER` live in memory until `CONFIG REWRITE` writes them to the configuration file as `user` lines, as Redis does when it has no `aclfile`. There is no `aclfile`, and `ACL LOG` is not implemented.
- `ACL SETUSER` accepts `sanitize-payload` and `skip-sanitize-payload`, but `RESTORE` payloads are always checked, so users always show `sanitize-payload`.
- `AUTH`, `HELLO`, `ACL` and `CONFIG SET requirepass` are kept out of the slow log, so passwords do not end up there. There is no TLS: on an untrusted network, passwords and data travel in the clear, so use a tunnel or keep the server on a private network.
